# Jev versus local models for context-aware Jira triage

Research checked 2026-09-24. This is a model-selection note, not a measured head-to-head benchmark on our tickets. Primary sources are linked beside claims. Project-specific requirements come from [instructions.md](../instructions.md) and [ANALYSIS.md](../ANALYSIS.md). The evaluation plan below reflects the team's later constraint: there will be no additional cases beyond the training corpus and blind set.

## The decision we actually need

The input is a **whole ticket and relevant surrounding evidence**: summary, description, request type, comments, current labels, service definitions, ownership map and, where useful, a few trustworthy historical examples. The output includes actual work type and affected service, urgency and impact inferred from consequences, an owner derived from the service map, and a defensible draft disposition/comment. A mislabeled SharePoint ticket about a delayed benchmark feed must be classified from the symptoms, not from its current folder, queue or literal service word. A generic “Emailed Support Tickets” bucket must be escaped only when the content supports a specific service. This is *contextual, multi-field adjudication*, not `email → folder`. See the [challenge specification](../instructions.md) and [revised local analysis](../ANALYSIS.md).

Keep the business rules in code: compute priority from inferred urgency × impact, resolve team from the service table, and review uncertain or consequential suggestions. Generated resolution text requires an LLM or sourced template; a decision-only model cannot write it. The existing PoC uses [Qwen3-4B-Instruct-2507 Q4_K_M through Ollama, intended for a 24 GB Mac mini M4](../README.md), with one constrained classification call and one draft-comment call per ticket. Its current [`num_ctx=4096` setting](../triage_poc/core.py) limits how much of a long ticket and catalogue it can actually read, regardless of the model's advertised maximum context.

Compare answer quality directly with Qwen; the card cautions that output can be inaccurate. |

No text generation. | **Interesting fast classifier experiment**, not a full triage solution. | **Rizzo Flow with a local LLM** | Apache-2.0 local wrapper over `llama.cpp`, default Spark-X2.5-4B Q8_0 download around **4.4 GB**, Jev-like API [project README](https://github.com/Rizzo-AI-Academy/rizzo-flow). | Reads answer-option logits instead of generating a JSON response, for typed decisions over a shared input. | A plausible way to reduce classification output work, but it is a **runtime/method**, not a separate trained reasoning capability. “Open source” needs precision. An **Apache-2.0 weight license** grants broad use/modification rights for the model artifact; it does not by itself prove that training data information and training code are available. The [Open Source Initiative AI definition](https://opensource.org/ai/open-source-ai-definition) requires those components for an Open Source AI system. Apertus explicitly publishes them; for Qwen, Ministral and Laya, describe the specific downloadable weights and software licensing rather than claiming complete training reproducibility. Jev's official SDK being MIT-licensed does **not** make the hosted Jev model open source. [TypeSafe's own System One adapter](https://github.com/typesafe-ai/system-one-adapter-python) can help run the same typed questions through an LLM endpoint, including a custom OpenAI-compatible endpoint, but adapter-requested probabilities are not evidence of calibration.

## Recommendation and fair test

1. **Keep the current Qwen baseline.** It already supports multi-field decisions and the resolution draft. The saved 20-ticket run takes 5.80 s/ticket across both calls; no reference answers establish that a smaller model preserves quality. Measure prompt length against its configured 4,096-token window, and increase that limit on the target machine only after checking memory and latency. Evidence-bearing output fields are a possible improvement, subject to validating their contents against the ticket.
2. **Treat Laya and Rizzo Flow as optional decision-only challengers**, with the *same* full state and service definitions. For Laya, measure truncation explicitly. For Rizzo, distinguish hard output constraints from measured quality and calibration. Neither writes the required comment; retain a generative step and human review.
3. **Treat Apertus 4B and Ministral 3B as optional generative challengers** if the core agent workflow is complete. Compare classification and comment quality separately, using the same output contract and target hardware. Apertus's 4K context makes retrieval selection part of the test.
4. **Use only the available training corpus and blind set.** The checked-in timestamped challenge export equals `sample_blind_eval_20.json`, and no new cases are available. The six labelled development fixtures give smoke checks for service and work type only. On the blind set, use label swaps, name masking, rules/model disagreement, repeat-run stability and deterministic output consistency as diagnostics, not as accuracy scores. Avoid tuning ticket-specific answers on the scored set. The synthetic 20K corpus repeats service names and templates, so accuracy on it alone would reward shortcuts rather than the task in the [official instructions](../instructions.md).

No model above has a cited, independently controlled head-to-head result for this project's contextual Jira triage. Model-card context lengths and vendor latency/benchmark claims are capability descriptions, not an accuracy ranking for our use case.

The repo's current [local analysis](../ANALYSIS.md) records **5.80 seconds mean per ticket** across 20 outputs for classification plus comment, and **6/6** work-type and **6/6** service on six hand-labeled development cases. Those are useful implementation baselines, but the six cases are small and the 20-output run has no independent reference answers. They should not be compared directly with TypeSafe's or Laya's published task benchmarks.
